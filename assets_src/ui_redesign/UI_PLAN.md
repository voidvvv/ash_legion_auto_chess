## 1. 草图解读

### 1.1 整体

- 横版画布，外框一条（本轮用图像模型复核的观感是「外粗内细」的双线边，可理解为面板自带边框），**没有任何箭头、把手、关闭钮、出售钮，也没有东西凸出外框**。
- 三个纵向分区，比例（协调方三通道读数，本轮复核基本吻合）：

| 分区 | 高度占比 | 内容 | 滚动条 |
|---|---|---|---|
| 上段 | 约 40~45%（复核约 38%：标题 6% + 预览区 32%） | 棋子名称标题；左=棋子图像预览（立绘位）；中=棋子描述；最右=纵向两个切换标签 | 描述框右缘一条纵向 |
| 中段 | 约 15~20%（复核约 13%） | 「已拥有的棋子（头像预览）」一行小方格，可见 6 格 | 紧贴格子行下方一条横向，几乎通栏 |
| 下段 | 约 35~40%（复核约 45%） | 左=装备栏网格；右=装备大图预览 + 装备描述 | 装备描述框右缘一条纵向 |

```

│ 棋子名称：兽人战士（标题）                      │
```

### 1.2 读法（协调方口径，本轮认可）

草图 = 抽屉**展开后的内部布局**；「左侧滑动」这个抽屉形态来自口头指令，草图本身没画抽屉怎么开、怎么关。中部「已拥有棋子头像条」= 备战席的替代形态（横向滚动）；下部 = 装备栏（左网格 + 右侧选中装备大图预览与描述）；上部 = 选中棋子的信息（立绘 + 描述 + 介绍/装备两标签）。

### 1.3 本轮复核补充（不改协调方口径，只加三条观察）

1. **画布长宽比**：草图约 4:3、接近正方；而游戏虚拟画布是 640×360（16:9）。所以抽屉是一块「近方形的竖板」，不是通栏——这直接决定了它能放哪（见 §3.2）。
2. **装备网格格数**：本轮模型读数约 **5 列 × 4 行，手绘不规整，置信度中**（此前三种读数为 3×4 / 3×3 / 4×4+）。四个通道四个答案，**确属读数不一**，列入待确认 §5-Q1。
3. **标签**：两个标签上下排列（上「介绍」、下「装备」），没有画选中态标记（下划线/高亮都没有）。选中态怎么表现属素材与实现细节（见采购单 M05/M06）。

### 1.4 草图未定项（汇总，详见 §5）

| # | 未定项 | 一句话 |
|---|---|---|
| Q1 | 装备栏网格格数 | 四种读数，定不了 |
| Q2 | 开合触发、收起态、默认开还是关 | 草图无把手/关闭钮 |
| Q3 | 出售按钮去哪 | 草图没画出售；现版靠「拖到 ⑦ 出售区」 |
| Q4 | 头像条与备战席 9 格上限的关系 | 可见 6，另 3 格靠滚动？ |
| Q5 | 「装备栏」是背包库存还是选中棋子的三件装备 | 标签写「当前装备」、网格写「装备栏」 |
| Q6 | 战斗中抽屉什么状态 | 锁定/只读/可操作 |

## 2. 与现有实现的映射（全部代码实读）

### 2.1 先说一个绕不开的发现：界面坐标「上下是反的」

设计文档的坐标表（`docs/render_design.md:352-361`）是 **y 向下**的（① 顶栏 y=0..28 在最上，⑧ 商店栏 y=296..360 在最下）。但代码两个坐标系都是 **y 向上**：世界相机是默认 y-up（`BattleScreen.java:163`；`BoardGeometryTest.java:27` 断言「行 0 在顶：py 大」），UI Stage 也是 y-up（`TopBar.java:37` 用 `VIRTUAL_H - 18` 贴顶）。

代码里只有两处做了翻转换算：④ 棋盘（`BoardGeometry.cellCenterY`，`BoardGeometry.java:137`）和 ⑧ 商店栏（`BoardGeometryTest.java:190` 的 `VIRTUAL_H - SHOP_BAR_Y`，设计文档 `render_design.md:359` 自己也记了这笔「实机在底部」的漂移）。**其余 ②③⑤⑦⑨ 的表值被直接当成 y-up 坐标用了**：

| 区 | 设计表（y 向下）意图 | 代码实际落点（按 y-up 推算） | 证据 |
|---|---|---|---|
| ② 备战席 (20,48,108,120) | 左上 | **左下**（商店栏上方） | `BoardGeometry.benchSlotCenter` 不翻转，`BoardGeometry.java:164-169` |
| ③ 装备背包 (20,172,108,72) | 左中偏下 | 左中偏上 | `BoardGeometry.java:190-195`、`InventoryPanel.java:88-91` |
| ⑨ 通知 (20,244,128,46) | 左下（商店栏上方） | **左上**（顶栏下方） | `NotificationPanel.java:148-149` |
| ⑤ 羁绊面板 (508,48,112,144) | 右上 | **右下** | `SynergyPanel.java:38` |
| ⑦ 出售区 (564,246,56,46) | 右下 | **右上** | `BattleRenderer.java:217`、`BoardGeometry.java:184-187` |

旁证：备战引导文案写「拖至**右下**出售区卖出」（`BattleRenderer.java:39`），而 ⑦ 实际画在右上；多处测试注释把「y 大」叫「下/底」（`BoardGeometryTest.java:108,205,214`）。

**我没法跑游戏，以上是代码推定**，需要实机瞄一眼确认（§5-Q10）。它对抽屉方案的影响很实在：抽屉要替掉 ②③、要和 ⑦ 打交道，写方案必须按**实机落点**来，不能按设计表。
>
> **实施期已实机证实**（事实清单 §7）：三张探针截图均显示出售区在右上；引导文案的方位词已改为由常量派生的「右上」（见 §7.7）。镜像漂移本身仍按 Q10 另案处理。

### 2.6 全局缩放与边缘断言（位图 UI 的命门）

- **缩放系数**：`GameBalance.RENDER_GLOBAL_SCALE = 0.8f`（`config/GameBalance.java:29`；`GameBalanceTest.java:266` 锁值）。
- **UI 域**：Stage 根节点整体缩放并居中，`BattleScreen.applyGlobalUiScale`，`:249-255`（根 scale 0.8、位置 (64,36)）；弹窗域同样处理，`:242`。内容矩形 `BoardGeometry.uiContentRect`，`:108-112` → (64,36,512,288)。
- **世界域**：镜头 zoom = `(1 + (1.06−1) × chromeFadeAlpha) / 0.8`，`render/ui/BattleTransitionController.java:171-174`。备战期 1.325（内容约 0.755 倍），战斗期 1.25（内容 0.8 倍）。**备战期两域缩放并不相等**（UI 0.8、世界约 0.755），只在转场结束时对齐到 0.8。
- **默认窗口 1280×720**（`lwjgl3/src/main/java/com/voidvvv/kz_auto_chess_n/lwjgl3/Lwjgl3Launcher.java:31`），视口再放大 2 倍。
- **于是**：今天任何 UI 位图的一个像素，到屏幕上是 **0.8 × 2 = 1.6 个屏幕像素**；世界域备战期件约 1.51。都不是整数。
- **边缘断言**：`core/src/test/java/com/voidvvv/kz_auto_chess_n/render/RenderScaleFitTest.java`——缩放矩阵 {0.7,0.8,0.9,1.0}（`:20`）下：世界域元件（④②③⑦）完整可见（`:26-49`）、UI 内容矩形不出视口（`:51-59`）、两域同屏心（`:61-77`）、悬停卡走廊不侵入棋盘（`:79-89`，注意它用同一个 scale 算卡和棋盘，是简化）、放大档必出屏的公式锁（`:91-104`）、s=0.8 回归锚（`:106-122`）。抽屉进场后这套断言要扩（§4.4）。

## 3. 交互设计

> 本章的数字都是**提案**，用来把问题说清楚；最终几何、开合方式、默认态都要主人点头（§5）。

### 3.1 抽屉结构是怎么定的（一段话）

草图被读成「抽屉展开后的内部布局」：一块近方形的竖板，自上而下三段——上段是**选中棋子的信息**（标题板写棋子名；左边立绘位；中间是可滚动的棋子描述；最右一列上下两个标签「介绍 / 装备」用来切描述区内容），中段是**已拥有棋子条**（一行 6 个可见头像格 + 下方一条横向滚动条，取代现在屏上的 3×3 备战席），下段是**装备区**（左边装备网格，右边选中装备的大图预览和可滚动描述）。「从左边滑出来」这个抽屉形态来自口头指令；草图没画把手、关闭钮和收起态，所以「怎么开、默认开不开、收起后剩什么」没法从图上读出来，单列待确认。

- 棋盘屏幕左缘 ≈ 247.5，**左边只剩 247 的宽度**；

### 3.3 开合方式：三个候选

| 候选 | 做法 | 好处 | 坏处 |
|---|---|---|---|
| **A · 把手开合**（倾向） | 左缘常驻一个竖把手；点把手滑出/滑回；点抽屉外任意处或 Esc 收起；**从抽屉里把棋子往外拖时面板自动让位**（淡到三成透明并退到一边），松手后保持收起 | 显式、可预测、触屏可用；主循环「买→放上→拖上棋盘」不受打扰 | 多一次点击才能看到全部后备 |
| B · 贴边悬停展开 | 指针贴近左缘就滑出，离开就收 | 少一次点击 | 把棋子拖去棋盘的路必经抽屉边缘 → 拖拽中要硬锁展开；布阵时指针常路过左缘 → 误开误关 |
| C · 选中即展开 | 点棋子/商店卡/装备就滑出显示它；没有选中且指针离开就收 | 信息型抽屉的常见做法 | 和拖拽主流程叠在一起状态容易乱（拖完要不要留开？） |

倾向：**A 做底座**，再叠一条「抽屉开着时，点选谁就显示谁」；B 不做；C 可作为可选加分（见 Q2）。

动效口径：滑出/滑回 0.18~0.25 秒、先快后慢；位移逐帧取整到整虚拟像素（像素规则，沿用 `BattleTransitionController.snap`，`:176-179`）；「拖拽让位」只做透明度 + 左移，不做弹跳。

**已裁定的行为（2026-11-22；第 1、2 条是实施期追加裁决，第 3 条随 Q2/Q6 定案）**：

- **点棋子 = 选中并展开抽屉**（维持）。给棋子穿上装备后，即选中该棋子。
- **装备待定态期间，点抽屉外不收起**：点装备进入待定后，点抽屉外面不会把抽屉收掉（否则没法去点棋盘上的棋子完成穿戴）；把手、关闭钮、Esc 仍然可以收起；待定清除后恢复「点抽屉外即收起」。
- **战斗期：默认收起、允许只读展开、任何相位跳变强制收起**（详见 §3.4）。
- 开合按 A 案全部落地：左缘竖把手点击开合；点抽屉外或 Esc 收起；收起留把手（角标「后备 n/9」）；默认收起；战毕不自动恢复展开；从抽屉往外拖棋子时面板让位（实施为强制收起 + 0.3 淡色）；开合 0.2 秒 ease-out。

### 3.4 两态：备战期 / 战斗期

- **备战期**：可开合；可拖拽上阵、拖去出售区、两段式穿装备、卸下、点选查看。**点棋子 = 选中并展开**（已裁定）。
- **战斗期**：**默认收起、允许只读展开看属性、禁止一切写操作**（Q6 已裁定）；**任何相位跳变强制收起**（2026-11-22 追加裁定）。只读展开只显示战前最后选中的棋子，不提供切换（2026-11-22 终审裁决接受，见 §5.1）。战斗期只读展开会压到棋盘第 0 列约 2.8 虚拟像素（战斗期棋盘比备战期略大，见 §6 的 R8）。

### 3.5 层级与输入路由

**绘制层级**（uiStage 内，自下而上；实施后的实际序见 `BattleScreen.uiLayerOrder`）：① 顶栏 → ⑥ 开战钮 → 战斗 HUD → 横幅 → 终局面板 → ⑧ 商店栏 → ⑤ 羁绊 → **⑨ 通知 → 抽屉层** → 悬停卡 → 转场收点。

> **追加裁决（2026-11-22，A 案）**：抽屉层放在 ⑨ 通知**之上**（方案原稿写的是「抽屉 → 羁绊面板/通知」，即抽屉在通知之下）。代价：抽屉展开期间，通知被整块盖住；按 L 键展开的通知大窗，左半也被盖。

抽屉在左、悬停卡里只有「备战期棋盘卡」和它冲突——展开时抑制这张卡（含备战期敌阵侦察虚影的悬停卡；侦察请先收起抽屉——2026-11-22 终审裁决接受，见 §5.1），抽屉自己的信息区顶上。

**输入路由的关键一招：触摸穿透。** uiStage 排在 boardProcessor 前面（`BattleScreen.java:318-324`），抽屉若照常可触摸，会把落在它范围内的事件全吞掉——而「拖棋子上阵」整条链子在 boardProcessor 里（`BoardInputProcessor.java:88-145`）。所以：

1. 抽屉的**面板底、头像格设成不可触摸**，只有把手、关闭钮、标签、滚动条滑块、装备格可触摸。点在头像格上的事件就穿过 uiStage 落到 boardProcessor。
2. 给 `BoardInputProcessor` 注入一个很窄的命中接口（例如 `int stripSlotAt(int screenX, int screenY)`），由抽屉实现——只有它知道自己滚了多少、滑到哪了。boardProcessor 的 `unitAt` 把「备战席矩形」那一支换成这个接口，返回的槽号仍然是 bench 下标，**后面拖拽、出售、死区点击的代码一行不用动**。
3. 滚轮现在没人接（`BoardInputProcessor.java:245-248` 恒 false）：描述框和装备描述用 scene2d 的 `ScrollPane`（可拖可滚）；头像条因为格子穿透了，只支持滚轮 + 拖滑块。
4. 弹窗（宝箱/暂停）在更上层的 dialogStage，照旧压住一切；转场期的全屏收点照旧吞点击，再加上「转场窗口内不许开合抽屉」。
5. 点棋子（棋盘上或头像条上）不再弹模态详情框，而是让抽屉**选中并展开**——详情弹窗已整体退役（Q5 裁定，事实清单 §6）。

**实施后的实际输入分层**（事实清单 §3）：`dialogStage` → `DrawerOutsideTouchProcessor`（新增的一层，**永不吃事件**：抽屉开着且按下点在抽屉外 → 抬手时收起；转场窗口或装备待定态下不收起；把手/关闭钮/Esc 直连控制器，不受影响）→ `uiStage`（抽屉在 `UnscaledLayer`：把手/关闭钮/标签/滑块/装备格/描述滚动框可触摸，头像格与底板穿透）→ `BoardInputProcessor`（头像条与装备格的命中经 `DrawerHitTest`，用**屏幕坐标**；滚轮落在头像条/装备网格上由它路由，`amountY>0` = 向下 = 看后面）→ `GlobalKeyProcessor`（Esc 先收抽屉，再开暂停）。

备选做法是「抽屉自己管拖拽」（在格子上挂监听，松手时自己把舞台坐标换算到世界坐标判落点）。能做，但死区、拖拽幽灵、落点高亮要再写一遍，不推荐。

### 3.6 重点论证：位图 UI 在 0.8 非整数缩放下的像素风险与对策

**事实链**（均有锚点，见 §2.6）：默认窗口 1280×720 → 视口 ×2；UI 根缩放 0.8 → **每个 UI 位图像素落在 1.6 个屏幕像素上**；项目像素规则是 Nearest 过滤 + 整数吸附（`docs/render_design.md:21`）。

**会出什么问题**：

1. **像素宽窄不一**。5 个素材像素要铺满 8 个屏幕像素，必然有的占 1 列有的占 2 列。1px 的描边、刻线、九宫格边线时粗时细，最显眼。
2. **滑动一顿一顿**。位移按整虚拟像素吸附，而 1 虚拟像素 = 1.6 屏幕像素，每帧走的不是整数屏幕像素。
3. **小字发虚**。12px 位图字体现在实际是以 9.6px 在渲染，笔画发糊；抽屉里偏偏全是小字描述。
4. **1px 细节可能整行丢**。分隔条、滚动条轨这种 1px 高的件，在非整数采样下有的位置 1 行、有的 2 行。

**三条对策**：

- **对策一（倾向）：抽屉走「不缩放层」。** 在 uiStage 根下加一层做反向缩放（scale 1/0.8 = 1.25，位置 (−80, −45)），正好抵消根缩放。效果：抽屉里 1 虚拟像素 = 1 舞台像素 = 2 屏幕像素（默认窗口），位图逐像素清晰、滑动步进是整 2px、文字 12px 原生。
  代价要说清：① 抽屉里的字会比其余 UI（等效 9.6px）大 25%——用悬停卡现成的 0.75× 字号（`HoverPreviewCard.CARD_TEXT_SCALE`，`:38`，合 9px）可基本抹平；② 备战期两域缩放本来就不等（UI 0.8、世界约 0.755），抽屉和左列/棋盘的对齐要按舞台坐标单独算一次（§3.2 的数字就是这么来的）；③ 用户把窗口拉成非 2 倍（比如 1600×900 是 2.5 倍）时，清晰保证失效——这是全游戏既有条件，不是抽屉带来的。
- **对策二：抽屉留在 0.8 层，素材按 1.25 倍尺寸出图。** 好处是与其余 UI 完全同尺度；坏处是上面 1、2、4 三条躲不掉，而且 1.25 倍的尺寸不整（槽 34 → 42.5）。不推荐。
- **对策三（治本但超范围）：把「根缩放 0.8」改成「布局和素材整体按 0.8 重出」。** 波及顶栏/商店栏/HUD/弹窗/悬停卡全部重排重出图。只登记，不在本次做。

无论选哪条，**素材出图规范都要配合**：线宽不小于 2px、不靠 1px 细节传达信息、九宫格四角取偶数——已写进采购单。

### 3.8 与开战转场的衔接

- **开战**：抽屉若开着，随转场一起左滑退场——直接复用 `poseExit`（`BattleTransitionController.java:127-132`），但退场距离要参数化（现在写死 140，小于抽屉宽度，会滑不干净）。② 的世界域绘制退役后，`benchOffsetX` 只剩出售区/提示/敌阵虚影在用，它们本来就主要靠淡出。
- **战毕回备战**：反向转场把抽屉滑回「收起态把手」，不自动展开；要不要恢复战前的开合状态见 Q2。
- **同帧叠加**：转场窗口内禁止开合抽屉（并入现有 `isInputBlocked` 那一位，`BattleTransitionController.java:90-93`）。
- **实施口径**（事实清单 §3/§6）：任何相位跳变强制收起（由抽屉自己的控制器执行）；`BattleTransitionController.benchOffsetX()` 已退役。上面「复用 `poseExit`、退场距离参数化」是开工前的设想，实施是否照做清单未记。

### 4.2 素材接入：`Assets` / `PlaceholderArt` 契约怎么扩到 UI 件

- **新建 `render/UiArt`**，和 `RealArt` 同构（对照 `render/RealArt.java:21-62`）：根目录 `art/ui/`，按 `{id}.png` 懒加载、Nearest 过滤、缺文件缓存 miss、统一 dispose。

- **文件形态**：先逐 key 单 PNG（和单位帧一致，二十来个文件）；以后要合图集再上 TexturePacker（lwjgl3 模块已带 gdx-tools，`lwjgl3/build.gradle:35`）。
