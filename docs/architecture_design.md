## 一、三态域模型（一切交互的路由规则）

任何用户交互先判定它改变**哪个域**的状态，再决定归宿：

| 状态域 | 内容 | 事件归宿 | 特权 |
|--------|------|----------|------|
| **局内模拟态** | 金币、名单、棋盘、轮次、随机种子 | 翻译为命令 → `CommandManager` 队列 → tick 消费 | 可回放、确定性 |
| **局外档案态** | 英雄/场景解锁、熟练度、传说进度 | 档案语义调用（轻量 handler） | 可持久化，**无回放需求** |
| **纯 UI 态** | 高亮、悬停、屏幕导航、设置开关 | Screen / Actor 自身状态 | 哪边都不进 |

判定示例：点击英雄卡片＝UI 态（高亮）；点击“开始远征”＝**域边界事件**，把 UI 态结算为 `StartRun(heroId, sceneId, seed)` 的参数——它是回放流的第 0 条记录。

## 二、实体管理

### 2.1 双实体（已定 2026-08-20）
- **`Unit`（名单实体）**：模板、星级、装备三槽。准不变——结构性变化（升星/穿装/出售）以新对象替换。轮与轮之间持久，**绝不被战斗污染**。
- **`BattleUnit`（战斗实例）**：`StartBattle` 时从名单派生——把羁绊（2/4/6 门槛）与装备加成**结算进属性快照**，附带可变战斗态（当前 HP、能量、网格坐标）。战斗结束**整体丢弃**。
- 收益：1C-R 重试＝免费（丢掉重新派生，零清理）；羁绊结算有了明确时机；回放确定性（同样名单 + 同样种子 = 同样战斗）。

### 2.2 单一 id 空间与 UnitRegistry（已定）
- **int 自增 id，一套空间覆盖三类实体：名单棋子、装备实例、战斗实例**（含敌方）。
- 发号器（id 计数器）归 `RunState` 持有——存档/回放时 id 序列天然可复现。
- `UnitRegistry` 是纯解析层：`add / remove / getById / iterate` + 发号，**不含任何业务逻辑**（买卖合成规则在 systems）。
- 边界处走 id 解析（命令载荷是纯数据），系统内部调用传对象引用——两者不冲突，冲突的只是“跨边界传对象”。

### 2.3 所有权地图（一个集合只有一个主人）

| 持有者 | 持有内容 | 生命周期 |
|--------|----------|----------|
| `RunState` | 轮次、场景、**当前逻辑阶段（命令门控查询入口）**、怜悯计数、随机种子、**id 发号器**、命令历史 | 一局 |
| `Player` | 金币/经验/等级 + **名单**（备战席 + 上场部署表） | 一局 |
| `BattleState` | **战斗实例集合** + 6×7 棋盘占位 | 一场战斗 |
| `ShopSystem` | 5 个槽位（模板引用 + 价格，**非实例**） | 一轮 |
| `UnitRegistry` | `id → 实例` 统一解析 | 一局 |

### 2.4 三层不可变（已定）
1. **静态模板**（`UnitData`/`SkillData`/`SynergyData`/`EquipmentData`）：完全不可变，加载一次终身只读；
2. **名单实体**（`Unit`、装备实例）：结构性变化 = 替换新对象，准不可变；
3. **战斗模拟态**（`BattleUnit`）：**受控可变**——身份不可变（id/模板/所属），模拟态在战斗作用域内直接改字段、出作用域即弃。这是对“不可变优先”规则的显式例外（60fps 逻辑步中 HP/能量高频变化，逐次替换会制造 GC 压力，Android 低端机风险真实存在）。

### 2.5 不上 ECS（已定）
场上 ≤ 20~30 实体、阶段制流程、无海量同质实体，ECS 的收益（cache 友好批量迭代）兑现不了，成本（概念负担/调试/依赖）全额支付。采用 **OO 实体 + registry + system 方法**，与命令架构严丝合缝。若未来出现数百级召唤物/投射物再评估。

## 三、局外档案层（已定：方案 A 轻量语义调用）

- 档案层**不建命令队列/不序列化命令流**——档案操作极少（开始远征/放弃）且即时语义；
- 但**硬约束**：解锁判定、熟练度结算必须抽成纯函数/纯服务类，禁止写进按钮 ClickListener——“Screen 只做点火器”原则在菜单层的延伸；
- 将来若需要升级为完整命令族（方案 B），是平移不是重写。

## 四、命令系统

### 4.1 命令全集（11 个，已定）

**经营类（SHOPPING）**

| 命令 | 载荷 | 语义与系统反应 |
|------|------|----------------|
| `BuyUnit` | `slot` | 购买入备战席；凑齐三个同名同星 → **自动 3 合 1**（后果，非命令） |
| `SellUnit` | `unitId` | 板上/席上皆可；返还按 GDD 3.6；卖场上棋子同步释放人口 |
| `RefreshShop` | — | 扣 2 金整批替换（轮首免费那次是系统行为，非本命令） |
| `BuyExp` | — | 扣 4 金加 4 经验；升级则人口上限提高 |
| `MoveUnit` | `unitId, target` | 统一语义：上场/下场/走位；target 为备战格或棋盘格（第 4~6 行）；目标格被己方占用 → 交换 |
| `EquipItem` | `itemId, unitId` | 背包→棋子；槽位由装备类型推导（武器/盔甲/饰品） |
| `UnequipItem` | `itemId` | 棋子→背包 |

**战斗与结算类**

| 命令 | 载荷 | 语义 |
|------|------|------|
| `StartBattle` | — | 派生 BattleUnit + 羁绊快照（处理过程）；**零棋子允许开战**（已定） |
| `Surrender` | — | 战斗中投降，立即判负，原地重试（已定保留） |
| `PickChest` | `option` | 三选一；宝箱内容进入 RESULT 时已 roll 好，本命令不消耗随机数 |
| `AbandonRun` | — | 放弃远征，流终止；按已达波数结算部分熟练度（已定保留） |

### 4.2 明确排除（防止概念混淆）

| 操作 | 归宿 |
|------|------|
| 侦察敌阵 / 棋子 Tooltip / 宝箱浏览 | 只读，UI 态 |
| 战斗加速 ×1/×2、暂停 | 表演层（accumulator 消费速率），不改逻辑 |
| 键位（如 D=刷新） | 输入方式，翻译层产出同一命令 |
| 自动 3 合 1 / 怜悯金币 / 宝箱 roll / 敌阵生成 | 确定性系统反应 |
| 英雄/场景选择过程 | UI 态；结果成为 `StartRun` 参数 |
| 存档 | 快照模型（§八），与命令流回放是两种持久化 |

### 4.3 校验原则
- Handler 执行前先做**纯确定性校验**（禁止时间、禁止掷随机），不合法命令**静默忽略 + 记日志**——否则回放会分叉。

### 4.4 tick 配对与回放模型
- 命令入队时由 `CommandManager` 盖 tick 戳，历史以 `(tick, command)` 保存（tick 由管理器记录，不污染命令纯数据）；
- **回放 = `StartRun(heroId, sceneId, seed)` + 命令流**；流终点 = 最终 Boss 轮的 `PickChest` 或 `AbandonRun`。

## 五、阶段状态机

### 5.1 状态与转移

```
新轮进入：轮次+1 · 生成敌阵(轮内固定) · 商店免费刷新 · 侦察就绪
   ┌──────────────────────────────────────────────────────┐
   ▼                                                      │
SHOPPING ──StartBattle──▶ BATTLE ──判胜──▶ RESULT ──PickChest─┤（非最终轮）
   ▲                      │  │                              │
   │      判负(全灭/超时/投降)│  └─Surrender─▶ 判负            │
   └───────────────────────┘                               │
   重试回备战：轮次不变 · 敌阵不变 · 商店不变 · 怜悯计数+1      │
                                                    最终Boss轮 ▼
                                                 RUN_END ▶ RunResultScreen
   任意局内阶段(备战/战斗)暂停菜单 ──AbandonRun──▶ RUN_END（按波数结算熟练度）
```

**关键区分——新轮进入 vs 重试返回**：只有前者触发轮次推进、敌阵生成、商店免费刷新；后者什么都不变，仅怜悯计数 +1。

### 5.2 命令门控矩阵

| 命令 | SHOPPING | BATTLE | RESULT |
|------|:---:|:---:|:---:|
| BuyUnit / SellUnit / RefreshShop / BuyExp / MoveUnit / EquipItem / UnequipItem | ✓ | | |
| StartBattle | ✓ | | |
| Surrender | | ✓ | |
| PickChest | | | ✓ |
| AbandonRun | ✓ | ✓ | |

### 5.3 轮开始事件（系统行为清单）
轮次 +1 → 按 GDD §7.3 半随机池生成敌阵（本轮重试不重掷）→ 商店免费自动刷新 → 侦察数据就绪 → 进入 SHOPPING。

### 5.4 判负路径
全灭 / 超时 60s / 投降 → 战斗态整体丢弃 → 回 SHOPPING（同轮重试）；本轮连续失败第 3 次起每次 +1 怜悯金币（**每轮至多 +3；零棋子战败不计入连败计数**——堵“空场秒投降刷保底”漏洞；计数器归 `RunState`）。

## 六、确定性细则

**RNG 消耗点全集**（四处）：
1. 轮开始的敌阵生成；
2. 商店刷新（轮首免费 + `RefreshShop` 命令）；
3. 宝箱内容 roll（进入 RESULT 时一次性）；
4. **战斗内暴击判定**（每次普攻 20% 概率 ×1.5，2026-08-20 评审整改拍板）——严格**按固定行动顺序**消耗。

**战斗随机仅限暴击判定一点**（原“战斗过程零随机”立场据此修订）：索敌、移动、技能全部为确定函数；暴击 RNG 按固定行动顺序消耗，同种子回放仍可完整复现。未来若新增战斗内随机（如“30% 概率眩晕”），必须经 `RandomGenerator` 并在此清单登记消耗点。

## 七、Screen 架构（6 Screen + 1 Dialog，已定）

**判定三问**（满足越多越应独立成 Screen）：资源域切换？输入架构重建？生命周期语义不同？  
**两类永不做 Screen**：弹窗/面板/对话框（归 Scene2D Dialog）；逻辑阶段（SHOPPING/BATTLE/RESULT 是逻辑状态机的状态，由 BattleScreen **观察**并切换 UI 可用性）。

| Screen | 绑定状态域 | 输入归宿 | 职责 |
|--------|-----------|----------|------|
| `LoadingScreen` | 无（资源进度） | 屏蔽 | AssetManager 加载 + 进度条 |
| `MainMenuScreen` | 档案域 | 档案语义调用 | 继续/新远征/图鉴/设置/退出 |
| `RunSetupScreen` | 档案域（解锁校验） | UI 态 → StartRun 参数 | 英雄选择 + 场景选择**两步式**合一 |
| `CodexScreen` | 档案域只读 | 无 | 图鉴/解锁/战绩 |
| `BattleScreen` | **局内模拟域** | **命令队列** | 棋盘+备战席+商店+阶段联动+暂停+宝箱，**内部零换屏** |
| `RunResultScreen` | 档案域写入 | 确认 | 点亮星辰演出 + 熟练度结算展示 |

- **设置 = 可复用 Scene2D Dialog**（主菜单与局内暂停菜单共用），非 Screen；
- 导航为浅图，各 Screen 直接知道去向，**不引入导航栈框架**；
- Android 生命周期：`BattleScreen.pause()` 只冻结 accumulator；进程被杀 → 下次从最近备战期快照恢复；
- 资源策略（MVP）：像素素材体量小，LoadingScreen **全量加载、永不卸载**，规避 Screen 间引用计数；
- 开发顺序：Phase 4 仅需极简 `MainMenuScreen` + `BattleScreen` 即可跑通核心循环，其余四个 Phase 5-6 补齐。

| 轨道 | 模型 | 内容 | 触发 |
|------|------|------|------|
| **快照轨**（挂起存档） | 全量状态序列化 | RunState + 名单 + 商店 + 档案；**存档点仅备战阶段**（已定） | 玩家挂起/退出；Android `pause()` |
